# SparkForge 实现说明

SparkForge 将自然语言需求转成可确认的产品蓝图，再生成结构化应用规格与源码文件，由内置预览组件呈现数据管理界面。当前已完成主要功能实现和一轮系统修复；真实线上“生成成功 → 数据操作 → 分享”仍受模型请求超时阻塞，尚未完成全链路验收。

## 实现思路与关键取舍

- **先确认蓝图，再构建应用。** Planner 生成 ProductSpec，用户确认后保存蓝图，Builder 生成 AppSpec 和源码文件。前后端校验结构、字段与引用关系；结构错误最多修复一次，避免无界重试。
- **结构化预览。** React/Vite 前端通过受约束的 AppSpec 渲染表单、集合和统计，而非直接执行模型生成的任意源码。这降低了运行不确定性，也意味着当前能力集中在数据管理类应用，并非通用应用部署引擎。
- **平台能力复用。** FastAPI 处理数据、分享和模型请求，使用 Atoms 的认证与云端能力。后端检查实体所有权和关联关系；公开分享仅提供必要的只读快照，不公开用户记录或源码。
- **交互先保证状态可信。** 已补充迟到响应隔离、操作期间防重复提交、失败保留表单、历史版本只读和输入法确认保护。暂停、恢复、停止会保存状态，但浏览器停止不等于服务端取消或停止计费。
- **保留可定位的失败。** 模型响应为空、截断、过滤时明确报错；预算由 4096 提升至 16384。流式方案在线上未验证成功，前端已恢复非流式调用，不能用延长客户端等待掩盖代理限制。

当前仓库以 `app/` 为唯一应用入口，替换旧 Next.js 原型；历史代码仍保留在 Git 历史中。

## 后续扩展与优先级

1. **P0：打通长任务执行。** 先确认 Atoms 对 SSE 的转发与缓冲行为，或改成持久化后台任务加轮询。已有明确的 120 秒代理超时证据，流式首事件也未在客户端响应头期限内到达。解决后立即补齐生成、CRUD、刷新、分享撤销及版本切换验收，这是当前主链路的阻塞点。
2. **P1：把任务一致性移到服务端。** 增加任务租约、幂等键、版本发布事务和明确取消语义；使用真实 PostgreSQL 验证并发、失败恢复与跨账号隔离。
3. **P1：补齐失败路径体验。** 非法项目 ID 使用中文提示和返回入口，补充应用级 404，统一侧栏与工作区状态，再验证真实移动端。
4. **P2：扩大应用能力。** 在稳定主链路基础上推进分页、结构变更后的历史数据处理、更多字段与视图，再考虑更自由的代码运行沙箱。避免在生成可靠性未解决前继续扩大模型输出规模。
